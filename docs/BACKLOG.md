## 一、功能缺口

### 1. PDF / DOCX 预览

- **来源**：`ROADMAP` P1-7（abcwyc 有）
- **现状**：没有。`file-kind.ts` 只认图片与音频（`grep -niE "pdf|docx" src/main/file-kind.ts` → 无命中）
- **为什么**：读文档不必离开应用。**但先看下面的数字**：现有的"用系统默认应用打开"通道（`openPathSafely`）
  已经把"我要看这份 PDF"这件事做掉了一半 —— 缺的只是"在应用里看"。

#### 测量结果（2026-09-19，同一进程、同一份 53 页 / 288 KB 的 PDF，窗口可见，用像素计数确认真的渲染了）

| 方案 | 打包体积 | 打开 53 页后内存 | 渲染 | 备注 |
| --- | --- | --- | --- | --- |
| Chromium 自带 PDF 阅读器 | **0 MB** | **+258 MB**（543 vs 285），**多 2 个进程** | ✓ 30.6 万非白像素 | `plugins: true` 即得；多出的进程打开后不会自己走 |
| pdf.js（6.3.289） | **3.58 MB**（min 脚本 1.71 + cmaps 1.11 + 标准字体 0.76；脚本 gzip 后 0.48） | **+110 MB**（456 vs 346），在已有渲染进程里 | ✓ 53 页 **826 ms** | 探针把 53 页全画成 canvas = 最坏情况（约 127 MB 画布）；只画可见页会更低 |
| DOCX：docx-preview 0.4.0 + jszip | ~1.67 MB（0.97 + 0.69） | 未测（纯 HTML 渲染，量级远低于 PDF） | — | 保真度尚可；mammoth（2.18 MB + 更多依赖）走语义 HTML，丢版式 |

**结论**：做的话选 **pdf.js** —— 它比自带阅读器**省 ~150 MB 且不新增进程**，代价是 3.58 MB 的包体（脚本 gzip 后 0.48 MB），
而且 worker 可以只在打开 PDF 时才加载。自带阅读器的 0 字节很诱人，但为一次预览常驻两个进程、并把一个**渲染不可信文件的插件**
带进应用的安全模型里，不划算。DOCX 单独排期（1.67 MB，收益比 PDF 低）。

- **验收标准**：先定范围 —— 只读预览（翻页 + 缩放），不做标注/搜索；沿用 `file-kind.ts` + 只读 IPC + 面板分支的形状；
  worker 懒加载（打开 PDF 才 import）；只渲染可见页；e2e 断言打开一份真实 PDF 后面板里出现非空白像素，关闭后进程数回到原值
- **下一步**：把上面这段测量写进 `ROADMAP` P1-7 的备注，并决定是否值得为"应用内看 PDF"花 3.58 MB（**决策点，不是实现点**）

## 二、有代价但值得的取舍（已在别处记过，尚未做）

### 3. CSP 换成 nonce / hash

- **来源**：`README.zh-CN.md` 安全节 + `ROADMAP` P2-14
- **现状**：聊天页与设置页都还是 `script-src 'unsafe-inline'`
  （`src/main/chat-adapter.ts:54`、`src/main/settings-window.ts:23`），注入点靠逐一 `esc()` 兜底
- **为什么**：现在 CSP 只防外联，不承担防 XSS；策略里去掉 `unsafe-inline` 才是那一层防线
- **成本**：改法不难（页面由我们自己拼，每个 `<script>` 上写 nonce），**难在验证**：
  聊天页里还有 vendored pi-chat 自己的内联 `type="module"` 脚本（那份 5.6M 字符的页面），漏一个就是白屏
- **验收标准**：页面上每一个内联脚本都有 nonce 或 hash，`unsafe-inline` 从两个 CSP 里消失，
  两套 e2e（含"无渲染层错误"门禁）全绿
- **第一步**：先做一次测量 —— 列出聊天页与设置页上**全部**内联脚本（数量、来源、能否被 nonce 覆盖），
  再决定 nonce 还是 hash

### 4. e2e 的偶发失败（记录，不是功能）

- **来源**：`KNOWN-ISSUES.md`（已闭环条目的补充段）
- **现状**：2026-09-19 观察到 **同一对** 检查在报告后小节偶发失败（会话窗口没画出对话 / 字号读不到节点，
  两者都是「子窗口还在读会话」）：隔离档 4 次里 2 次、只读档 4 次里 2 次，另一份代码下一次运行干净。
  已做两处降噪：等节点的时间 30s → 60s（harness 自己 seed 的是真实会话的副本，解析几十秒是正常的）；
  字号检查在没有节点可测时改成 `skip` 并给出 `--chat-fs` 与节点数，而不是报成字号缺陷
- **为什么**：门禁偶发 = 每轮都要人肉判断"这是真失败还是又抽了"
- **成本**：小到中，但**要先复现**：现在只有一次记录
- **验收标准**：连续 5 次只读运行 0 失败（与隔离档当初的收口方式一致），或让失败信息直接指出是哪一步。
  2026-09-19 降噪后：隔离档 1 次 149/0、只读档 1 次 83/0 —— 还差 4 次
- **第一步**：再跑 4 次只读 e2e 收口（失败时的 `conversation nodes` 与窗口正文已经在打印）

## 四、单独立项：跨平台（macOS / Linux）

- **现状**：打包目标只有 Windows（`package.json` → `build.win` 存在，无 `build.mac` / `build.linux`）
- **为什么**：最大的一条缺口，也是本机价值最低的一条（作者与主要使用者都在 Windows）
- **成本**：主要不在代码 —— `titleBarOverlay`、`node-pty`/conpty、托盘图标、自更新、深链，
  每一样都要在另外两套系统上**真机验证**；仓库的习惯是"打包后真的启动一次"，跨平台意味着这条验证 ×3
- **验收标准**：`npm test` + `e2e:isolated` 在 mac/linux 上跑通，且打包产物能启动一次
- **第一步**：可行性测量（能否在 mac/linux 上跑通那两条门禁），再决定排期；
  **在没做之前，README 与发布说明不应暗示支持 mac/linux**（现在没有暗示，保持这样）

## 五、明确不做（现在）

- **把 UI 换成另一个框架重写**：现有外壳的问题都是可定位的具体缺陷，重写换不来这些缺陷的解决。
- **在应用里内建 pi 的能力**（模型路由、工具编排）：边界很清楚 —— 能力由 pi 提供，我们负责宿主。
- **为"看起来功能多"而加的面板**：每加一个面板就多一份轮询、多一块内存（1.2.1 吃过一次这个亏）。
