# Roadmap / backlog

一份按**优先级与性价比**排序的待办清单，把两件已知缺陷和一轮同类产品对比得出的功能缺口放在一起。
这不是承诺的功能列表：每一项都写清**为什么值得做、怎么做、以及怎样算做完**，因为"做完"在这个仓库里
意味着**有测试**、而且**文档里的话都能被实测支撑**。

来源都标出来了：`KI` = 本文档同目录的 `KNOWN-ISSUES.md`，其余为同类项目的 README（在 §参考里列出）。

> **状态快照见 [`BACKLOG.md`](BACKLOG.md)**：本文负责排序理由，那份负责"现在到底有没有"（每项带核对命令）。

## 怎么排序

排序按 **性价比 = 用户价值 × 可验证性 ÷ 成本**，并对三类东西打折：

- **成本要用"带验证"来算**，不是"写完代码"。跨平台这种，成本主要不在写代码，而在三套系统上把终端、
  托盘、标题栏、自更新全部验一遍。
- **动到安全模型的项要降级**：凡是引入"渲染不可信远程内容"的面（内置浏览器就是这样），
  都要先设计边界，不能顺手加。
- **未知成本要先降成本**：先做一次决定性测量，再决定要不要排进去（字号那条就是标准例子）。

## P2 — 有价值，但要么重、要么动安全边界

| # | 事项 | 为什么排后面 |
| --- | --- | --- |
| 8 | 运行中断恢复（重开时接着跑） | 需要把 pi 的进行中状态落盘，并处理"恢复时上游已变"的冲突；价值中 |
| 9 | 自定义主题文件 / 主题市场 | 我们已有主题 + 任意强调色；再加一层文件格式与校验，收益主要是外观向 |
| 10 | 窗口内标签页（同窗多会话） | 与现有的"拖出成窗 + 窗口上限 + 会话独占写者"模型冲突，需要重新设计与仲裁 |
| 11 | Agent 舰队 / 受管进程面板 | 属于"多 agent 编排"，与 pi 自身的能力边界重叠，先看清 pi 的规划再动 |
| 12 | 内置浏览器 / 共享浏览器 | **动安全模型**：等于新增"渲染不可信远程内容"的面。必须单独设计边界（沙箱、CSP、权限、域名白名单）后才有资格排队 |
| 13 | 消息渠道（Telegram / 微信 / 飞书） | 每接入一个渠道都要凭据管理、权限模型、失败可见性；价值对特定用户很高，对其他用户为零 |
| 14 | **CSP 换成 nonce/hash**（现在聊天页与设置页都是 `script-src 'unsafe-inline'`） | 现在靠**注入点逐一转义**（`sidebar`/`dock`/`palette`/`settings` 各有 `esc()`），策略只防外联、不承担防 XSS —— 见 `README.zh-CN.md` 的安全节。改法不难（页面由我们自己拼，可在每个 `<script>` 上写 nonce），**难在验证**：聊天页里还有 vendored pi-chat 自己的内联 `type="module"` 脚本（那份 5.6M 字符的页面），漏一个就是白屏 —— 先做一次测量（列出页面上全部内联脚本、确认哪些能被 nonce 覆盖），再动 |

## 单独立项 — 跨平台（macOS / Linux）

**这是最大的一条缺口，也是本机价值最低的一条**（作者与主要使用者都在 Windows）。它应当单独排期，因为：

- 成本主要不在代码：`titleBarOverlay`、`node-pty` 预编译与 conpty、托盘图标、自更新、深链，
  每一样都要在另外两套系统上**真机验证**；
- 仓库的既有习惯是"打包后真的启动一次"（1.2.x 的发布说明里就有这一步），跨平台意味着这条验证要 ×3；
- 在没做之前，README 与发布说明**不应暗示**支持 mac/linux（现在没有暗示，保持这样）。

**建议**：先做一次可行性测量（能否在 mac/linux 上跑通 `npm test` + `e2e:isolated`），再决定排期。

## 明确不做（现在）

- **把 UI 换成另一个框架重写**：现有外壳的问题都是可定位的具体缺陷，重写换不来这些缺陷的解决。
- **在应用里内建 pi 的能力**（模型路由、工具编排）：边界很清楚 —— 能力由 pi 提供，我们负责宿主。
- **为"看起来功能多"而加的面板**：每加一个面板就多一份轮询、多一块内存，1.2.1 已经吃过一次这个亏
  （见 `KI` 的精简外壳条目）。

## 每个条目的通用完工标准

1. **有测试**：纯逻辑进 `test/*.test.cjs`；用户可见行为进 `scripts/e2e.cjs` 的一个 section。
2. **有实测**：性能/资源相关的改动要给出前后数字（1.2.x 的记录方式可以照抄）。
3. **文档同步**：`CHANGELOG.md` 写用户能感知的变化；`README` 的话必须能被实测支撑；
   没修好的进 `KI`，并写清**已排除什么**与**下一步测什么**。
4. **版本**：功能与修复走补丁位；小版本号留给重大更新（见 `docs/RELEASING.md`）。
